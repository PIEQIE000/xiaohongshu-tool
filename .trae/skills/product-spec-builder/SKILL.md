# Product Spec Builder

## 任务目标

本 Skill 用于：将用户模糊的产品想法转化为结构化的产品需求文档（Product Spec）

触发条件：
- 用户描述产品想法（如"我想做一个写作工具"）
- 用户提出功能需求（如"加个登录功能"）
- 用户说"帮我做一个XX项目"
- 用户提到"需求"、"PRD"、"产品规划"等关键词

## 核心原则

### 禁写令（最高优先级）

**Do NOT write any code, scaffold any project, or take any implementation action until the user has approved the final spec.**

无论项目看起来多么简单（一个 TODO 列表、一个配置修改、一个单页面），都必须走完整的需求收集流程。

### 反模式防御

以下借口一律无效：

- ❌ "这个太简单了，不需要 Spec" → 简单项目往往因未审视的假设导致最大浪费
- ❌ "我理解你的意思了，直接开始吧" → 理解≠明确，必须书面确认
- ❌ "我们可以边做边改" → 边做边改 = 反复返工

## 执行流程

### 步骤1：需求收集（一次一问）

当用户描述产品想法后，**一次只问一个问题**，逐个收集关键信息：

**追问维度**（按顺序）：

1. **核心目标**：这个产品要解决什么问题？目标用户是谁？
2. **核心功能**：最核心的 1-3 个功能是什么？
3. **交互方式**：用户如何与产品交互？（Web/App/CLI/对话式/编辑器）
4. **数据管理**：数据如何存储？需要持久化吗？
5. **边界情况**：有无特殊限制？（性能要求、安全要求、兼容要求）
6. **技术偏好**：有无技术栈偏好或限制？
7. **成功标准**：怎么算做完了？验收标准是什么？

**提问规则**：
- 一次只问一个问题
- 根据用户的上一个回答，推导下一个问题
- 不要发"需求调查问卷"式的一串问题
- 如果用户回答模糊，追问具体细节

### 步骤2：方案提案

收集完关键信息后，提供 2-3 种实现方案，每种包含：

- 方案描述
- 优缺点（Trade-offs）
- 你的推荐意见及理由

示例：
```
方案A：轻量级单页应用
- 优点：开发快、部署简单、维护成本低
- 缺点：扩展性有限、不适合复杂交互
- 推荐场景：MVP 验证、个人工具

方案B：全栈应用（前端+后端+数据库）
- 优点：功能完整、可扩展、支持多用户
- 缺点：开发周期长、维护成本高
- 推荐场景：正式产品、多用户场景

我的推荐：[根据用户场景给出具体建议]
```

### 步骤3：用户确认

等待用户选择或修改方案。**在用户明确批准前，不进入下一步。**

### 步骤4：生成 Spec 文档

用户确认后，生成结构化的 Product Spec 文档，保存到 `docs/specs/YYYY-MM-DD-<topic>-spec.md`。

## Spec 文档模板

```markdown
# Product Spec: [产品名称]

## 1. 产品概述
- 解决的问题：
- 目标用户：
- 核心价值：

## 2. 功能需求
### 2.1 [功能模块A]
- 功能描述：
- 用户场景：
- 验收标准：

### 2.2 [功能模块B]
- 功能描述：
- 用户场景：
- 验收标准：

## 3. 非功能需求
- 性能要求：
- 安全要求：
- 兼容性要求：

## 4. 技术约束
- 技术栈：
- 部署方式：
- 其他约束：

## 5. 边界情况
- [已知的边界情况和处理方式]

## 6. 成功标准
- [怎么算做完了]
```

## 输出格式

- 格式：Markdown
- 保存路径：`docs/specs/YYYY-MM-DD-<topic>-spec.md`
- 文件命名：日期 + 主题 + `-spec` 后缀

## 错误处理

### 常见错误及解决方案

1. **用户拒绝回答追问**
   - 处理：解释 Spec 的重要性，说明没有 Spec 的后果（反复返工）
   - 如果用户坚持，至少生成一份最小 Spec 让用户确认

2. **用户需求频繁变更**
   - 处理：记录变更，更新 Spec，标注版本号
   - 提醒用户：频繁变更会影响开发进度

3. **需求过于庞大**
   - 处理：主动建议拆分，先做 MVP（最小可行产品）
   - 拆分原则：每个 Phase 有独立可交付的价值

## 使用示例

### 输入示例

用户：我想做一个写小说的工具，能管理章节和角色设定

### 交互过程

AI：好的！让我先理解一下你的需求。这个写作工具主要解决什么问题？是帮你整理思路，还是纯粹的文本编辑？

用户：主要是帮我管理长篇小说的结构，章节多了容易乱

AI：明白了。核心是"结构管理"。那最核心的功能有哪些？比如章节管理、角色管理、大纲视图，你觉得哪些是必须的？

用户：章节管理和角色管理是必须的，大纲视图最好有

AI：好的。交互方式呢？你希望在浏览器里用（Web 应用），还是桌面应用，或者命令行工具？

用户：Web 应用吧，随时能打开用

[继续追问技术偏好、数据存储、成功标准...]
