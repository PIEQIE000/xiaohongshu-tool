# Dev Planner

## 任务目标

本 Skill 用于：读取 Product Spec 和 Design Brief，将需求拆解为可执行的开发计划，包含 Phase 拆分和 Task 拆分。

触发条件：
- 用户说"制定开发计划"、"拆解任务"
- Product Spec 和 Design Brief 确认后
- 用户提到"先做什么后做什么"、"开发顺序"
- 需要评估工作量或制定排期时

## 核心原则

### 任务拆分原则

- 每个 Task 必须是**可独立验证**的单元
- 每个 Task 预估 2-5 分钟可完成（AI 编码时间）
- 任务之间标注**依赖关系**
- 无依赖的任务可以编组到同一 Wave 并行执行

### 反模式防御

以下借口一律无效：

- ❌ "这个任务很简单，我一次写完" → 大任务容易迷失方向
- ❌ "后面再补测试" → 没有"后面"，先写失败的测试
- ❌ "这些任务可以合并" → 合并任务 = 无法定位问题来源

## 执行流程

### 步骤1：读取上下文

读取以下文档（按优先级）：
1. `docs/specs/` 目录下最新的 Product Spec
2. `docs/design/` 目录下最新的 Design Brief
3. 如果已有设计稿，以设计稿为准

### 步骤2：技术调研

针对需求涉及的技术栈，快速调研：
- 有无现成的开源组件可用？
- 有无成熟的模板或脚手架？
- 推荐的技术选型是什么？

### 步骤3：Phase 拆分

将项目拆分为多个 Phase，每个 Phase 有**明确的交付物**。

拆分原则：
- Phase 1：基础架构（项目初始化、依赖安装、目录结构）
- Phase 2：核心功能（按 Spec 中的功能模块拆分）
- Phase 3：增强功能（非核心但有价值的功能）
- Phase 4：优化与发布（性能优化、测试完善、打包发布）

### 步骤4：Task 拆分

将每个 Phase 拆分为多个 Task，每个 Task 包含：

- **Task ID**：T001, T002...
- **描述**：具体要做什么
- **涉及文件**：新建/修改的文件路径
- **验收标准**：怎么算完成了
- **依赖**：依赖哪些 Task
- **预估时间**：2-5 分钟

### 步骤5：Wave 分组

分析 Task 之间的依赖关系，将无依赖的任务编组到同一 Wave：

```
Wave 1: T001, T002, T004  ← 无依赖，可并行
Wave 2: T003, T005        ← 依赖 Wave 1
Wave 3: T006              ← 依赖 Wave 2
```

### 步骤6：自检

生成计划后，执行自检：

1. **覆盖检查**：每个 Spec 需求都有对应 Task 吗？
2. **占位符扫描**：有无 "TBD"、"类似 Task N" 这样的模糊表达？
3. **依赖检查**：Task 的依赖关系有没有循环依赖？
4. **粒度检查**：有 Task 超过 5 分钟预估时间吗？如果有，继续拆分

### 步骤7：用户确认

展示 Dev Plan，等待用户确认或修改。

### 步骤8：保存文档

保存到 `docs/plans/YYYY-MM-DD-<topic>-dev-plan.md`。

## Dev Plan 文档模板

```markdown
# Dev Plan: [产品名称]

## Phase 1: [Phase 名称]
**交付物**：[本 Phase 完成后的可交付成果]

### Task 列表

| ID | 描述 | 涉及文件 | 验收标准 | 依赖 | Wave |
|----|------|---------|---------|------|------|
| T001 | [具体描述] | [文件路径] | [怎么算完成] | 无 | 1 |
| T002 | [具体描述] | [文件路径] | [怎么算完成] | 无 | 1 |
| T003 | [具体描述] | [文件路径] | [怎么算完成] | T001 | 2 |

---

## Phase 2: [Phase 名称]
**交付物**：[本 Phase 完成后的可交付成果]

### Task 列表
[同上格式]

---

## Wave 执行顺序

```
Wave 1: T001, T002        ← 可并行
  ↓
Wave 2: T003, T004        ← 依赖 Wave 1
  ↓
Wave 3: T005              ← 依赖 Wave 2
```

## 技术选型
- [技术 A]: [选择理由]
- [技术 B]: [选择理由]

## 风险点
- [可能的风险和应对方案]
```

## 输出格式

- 格式：Markdown
- 保存路径：`docs/plans/YYYY-MM-DD-<topic>-dev-plan.md`

## 错误处理

### 常见错误及解决方案

1. **Spec 不清晰，无法拆分 Task**
   - 处理：回退到 product-spec-builder，要求先明确需求

2. **Task 拆分后用户觉得太碎**
   - 处理：解释小 Task 的好处（便于定位问题、便于并行）
   - 如果用户坚持，可适当合并，但不超过 10 分钟预估时间

3. **技术调研发现需要新技术栈**
   - 处理：在 Dev Plan 中标注，新增 Phase 0（技术预研）
   - 提醒用户：引入新技术会增加开发时间
